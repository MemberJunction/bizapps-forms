## Type
feature

## Problem
Most of Forms' domain logic runs only in the browser. Publishing (`packages/Angular/src/lib/builder/publish.service.ts`), cloning, template instantiation, archive and restore, distribution verbs, automation editing, and reporting are Angular services making raw entity calls; the server trusts whatever snapshot the builder wrote (`packages/Server/src/public-submit/snapshot-parser.ts`). Consequences, all verified on `next` @ e5691a6:

- An Action, an agent, the planned bizapps-tasks approval flow, or any host without Angular cannot publish a form, clone one, or archive one with the same result as the UI. The two AI authoring actions can only leave a Draft.
- Multi-row writes commit row by row with no transaction: clone (`form-clone.service.ts`, 7 save sites), the automation tab (20 call sites; reorder is two saves plus a compensating re-save), `buildFormFromBlueprint` in Actions, and the submit pipeline itself (`persistence.service.ts:725` says so). A failure leaves a half-copied form, a half-reordered automation list, or a response whose quota counter never moved.
- The quota is read-then-write (`persistence.service.ts:821-840`), so concurrent submits can exceed `MaxResponses`.
- On-submit automations run as a detached promise; a process killed in that window loses them. The recovery sweep (`packages/Server/src/automation/recovery-sweep.ts`) has no production caller.
- Rules exist twice and already disagree: `ValidationRule` application and the required-message text differ between `widget/core/validation.ts` and `Server/.../validation.service.ts`; the widget settles visibility in up to 5 passes while the server does a single pass.
- The respondent payload is a denylist (`public-form-payload.ts:103-105`, `{ ...definition, automations: [] }`), so the quiz answer key, every ending screen with its redirect URL, and the knockout conditions reach anonymous respondents (#302). The widget then picks the ending itself.
- Archiving sets `Form.Status` from the UI and the public path never checks `Form.Status` (`definition-loader.service.ts:155-186` checks only the distribution window and `FormVersion.Status`).
- Five pieces of state are process-local (`savesInFlight` in `FormDistributionEntityServer`, `FormsRateLimiter`, three `InFlightLimiter`s), so several API instances do not behave as one.
- The builder loads its graph with 4 sequential `RunView`s and saves structure one row at a time.
- The reporting tab loads every response and answer with `IgnoreMaxRows: true` and aggregates in the browser.

The target is MJ's standard shape: domain logic in server engines and entity server subclasses, exposed through typed Remote Operations, with thin clients. One PR covers every feature (decided 2026-10-12).

## Design decided

### 0. Line and sequencing
- **Target MJ `6.2.0-edge.3`** (the `edge` dist-tag; verified 2026-10-12). The Work Queue, `CreateIsolatedProvider()` and the Redis lease API exist only on 6.2. Remote Operations, `RunInEntityTransaction`, `ExecuteSQL` ambient-transaction semantics, `Dialect.AffectedRowCountSQL`, `RelatedRecordCollection`, `SaveEntityGraph`, scheduled jobs, the `@angular/*` pins and the `@memberjunction/ng-auth-services` peer set are byte-identical between v6.1.5 and `origin/next`, so nothing in the design depends on 6.1-only behaviour.
- **The pin bump is the first commit**, by itself, no behaviour change. Use the repo's own `.claude/skills/mj-upgrade/` runbook: `bump-pins.sh 6.2.0-edge.3` (a prerelease target moves the peers and `mjVersionRange` too), then `pnpm install --lockfile-only`, then `npm run lint:mj-ranges`. Do not hand-edit pins.
- **Core migration trap.** `origin/next` carries 33 migrations v6.1.5 lacks, and 28 of them (`V202609142100` through `V202610061614`) are versioned *below* v6.1.5's top file `V202610061630`. `mj migrate` defaults to `outOfOrder: false`, so a database at the 6.1.5 frontier would skip all 28 silently. **Build the sandbox database from scratch at 6.2.0-edge.3** (clean-room recipe in `docs/database-operations.md`); never migrate a 6.1.5 copy upward. Note `V202610061630` itself is absent on `next` (line-only, logged as applied-but-missing).
- **Merge gate.** `@mj-biz-apps/common-*` 5.52.0 peers on `^6.1.5` and `@mj-biz-apps/tasks-*` 1.7.0 on `^6.1.0-edge.5`; neither admits `6.2.0-edge.3` (semver admits a prerelease only on its own `major.minor.patch`), and `mj app install` installs them leaf-first before Forms. So the PR is **built and tested on edge in a sandbox with no sibling apps installed** (Forms only peer-imports their entity packages; no sibling server package is loaded by the submit path), and **merges only after** the 6.2 LTS ships, common and tasks publish releases whose MJ peers admit it, and this PR's pins are revved to that LTS tag with the same script.
- CodeGen on 6.2 narrows CHECK-constraint columns to literal unions, so regenerated entity output changes beyond the new file; expected. `CreateMagicLinkInviteParams` fields were renamed to PascalCase upstream without aliases; Forms does not call that service (its minter writes `MJ: Magic Link Invites` rows itself), so nothing to change.

### 1. Package graph and layering
Dependencies after the change: `forms-entities` ← `forms-core-entities-server` ← `forms-actions` ← `forms-server`; `forms-ng` depends on `forms-entities` only.

- **`forms-entities`**: `contracts/` (pure, browser-safe) plus CodeGen output, now including `generated/remote_operations.ts`, exported from `packages/Entities/src/index.ts`.
- **`forms-core-entities-server`**: every engine, every entity server subclass, every operation server subclass, the Work Queue handler, and the shared action helpers that today live in `forms-actions` (`custom/shared/form-response-context.ts`, `save-entity.ts`, `action-provider.ts`, `custom/binding/binding-executor.ts`, `binding-ledger.ts`, `MJBindingGateway`). Gains peers `@memberjunction/actions`, `@memberjunction/actions-base`, `@memberjunction/work-queue-engine`, `@memberjunction/work-queue-core`, and the `@memberjunction/ai*` / `communication-*` peers the moved helpers need. Listed in `mj-app.json` under `server` as a `library` (per #301: anything with server-only peers goes under `server`, never `shared`).
- **`forms-actions`**: thin `BaseAction` wrappers calling engines; adds a dependency on `forms-core-entities-server`. `Forms: Generate Form From Brief` and `Forms: Create Form From Template` gain an optional `PublishImmediately` boolean param (default false) and, when true, call `FormPublishingEngine` after building the draft. `buildFormFromBlueprint` moves into `FormAuthoringEngine` and runs in one transaction; it no longer creates a Draft `FormVersion` row (nothing reads the `FormVersionID` output; publish uses max+1 so the Draft only made the first published version v2).
- **`forms-server`**: transport only. HTTP middlewares (host page, redeem, resume, upload, asset, download, widget bundle, request identity, stacktrace redaction), `RESOLVER_PATHS` (generated resolvers only), minter registration. `public-submit/`, `automation/`, `distribution-claims/`, `PublicFormResolver.ts`, `DistributionClaimsResolver.ts`, `isolated-provider.ts`, `isolated-dispatcher.ts` and `recovery-sweep.ts` are moved or deleted. The HTTP endpoints' access and provenance decisions become engine calls.

### 2. Remote Operation rails (first in this repo)
- `mj.config.cjs` `output` gains `{ type: 'RemoteOperations', directory: './packages/Entities/src/generated' }`. CodeGen resolves the `Forms.` key namespace to `__mj_BizAppsForms` through the `MJ_BizApps_Forms: Forms` entity name, which is inside `includeSchemas`.
- New metadata directories, added to `metadata/.mj-sync.json` `directoryOrder`: `remote-operation-categories/` (one category, "Forms"), `remote-operations/` (one record per operation below, `GenerationType: Manual`, `ExecutionMode: Sync`, `RequiresSystemUser: false`, `CodeApprovalStatus: Approved`, `Status: Active`, `InputTypeDefinition`/`OutputTypeDefinition` as `@file:types/<key>.input.ts` / `.output.ts`), `queries/` (reporting), `work-queue-topics/` and `work-queue-subscriptions/` (outbox), `entity-relationships/` (builder graph). Model each file on `bizapps-orders/metadata/remote-operations/` (the full metadata→CodeGen flow; bizapps-accounting does **not** use it, contrary to the issue text). Records carry a `uuidgen` primaryKey and no `sync` block; no `Metadata_Sync` migration.
- **Type files contain no `import` lines**: CodeGen emits them verbatim into `remote_operations.ts`. They are the single source of I/O types; every consumer imports the emitted types from `@mj-biz-apps/forms-entities`. The widget uses `import type`, which is erased, so `widget-bundle-guard.mjs` is unaffected. Outputs that carry a definition carry it as JSON text; the widget parses it with the contracts zod schema.
- Each server operation: `@RegisterClass(BaseRemotableOperation, 'Forms.<Name>')`, extends the generated base, validates input (throw with a `Forms.<Name>: …` message; throws arrive as `ResultCode: 'EXECUTION_ERROR'`, `ErrorMessage`), calls exactly one engine method, maps the result. Exports an empty `Load<Name>Operation()` anchor called from `LoadBizAppsFormsServer()`; `forms-server`'s `index.ts` imports `forms-core-entities-server` after `forms-entities` so the server subclass registers last.
- **`Authorize()` is the only gate the operation controls.** `RequiredScope` is enforced only for API-key sessions; an in-process `.Execute()` skips the resolver gates entirely; an anonymous magic-link session can reach any Active operation, `MJ.SaveEntityGraph` included. Authoring ops require `!user.IsMagicLinkAnonymous && !user.MagicLinkScope` and `CanUpdate` on `MJ_BizApps_Forms: Forms` via `EntityByName(...).GetUserPermisions(user)` (the `canUpdateDistributions` precedent in `claims.service.ts`). Respondent ops require a magic-link session whose `MagicLinkScope.ResourceID` equals the distribution resolved from the input slug, or the response id on resume. `IsScopeLimitedPrincipal` is not exported from `@memberjunction/server`; check the two `UserInfo` flags directly.
- Engines are `BaseSingleton`s; methods take `(provider: DatabaseProviderBase, user: UserInfo)` and use `RunInEntityTransaction(provider, …)`. Counters use `provider.ExecuteSQL` with `provider.Dialect.AffectedRowCountSQL(dml, 'n')` on the **same provider instance** so they join the ambient transaction (`ExecuteSQL` is not on `IMetadataProvider`; it is public on `DatabaseProviderBase`). Background code uses `CreateIsolatedProvider()` from `@memberjunction/server`.
- Entity-subclass invariants live in `ValidateAsync` (opt in with `DefaultSkipAsyncValidation => false`) using `GetFieldByName(x).OldValue` / `.Dirty` and `IsSaved`, with a `Save()` override for the `ReplayOnly` path. Engine-only privileges use a public transient field on the subclass (precedent: `BypassBookedCheck` in bizapps-orders `OrderLineEntityServer`), which `SaveEntityGraph` never serialises, so a browser cannot set it.

### 3. Operations
| Operation | Input → Output | Replaces |
|---|---|---|
| `Forms.PublishForm` | FormID → FormVersionID, VersionNumber, RetiredVersionIDs | `publish.service.ts` |
| `Forms.CloneForm` | SourceFormID, Name?, AsTemplate → FormID | `form-clone.service.ts` |
| `Forms.CreateFormFromTemplate` | TemplateFormID or TemplateKey, Name? → FormID | `form-templates.service.ts` instantiate; the template Action's body |
| `Forms.ArchiveForm` / `Forms.RestoreForm` | FormID → Status | `forms-home.service.ts` setStatus |
| `Forms.IssueDistributionLink` / `ReissueDistributionLink` / `OpenDistribution` / `CloseDistribution` | FormID + ChannelType on issue, else FormDistributionID → id, Slug, RespondentURL | `distribution.service.ts` verbs; slug generation and its 5-attempt retry move server-side |
| `Forms.GetDistributionClaims` | FormID → claims, failures | `DistributionClaimsResolver` |
| `Forms.SaveAutomation` / `ReorderAutomations` / `RemoveAutomation` | FormID + automation and optional binding; ordered ids; FormAutomationID → ids | `automation-tab.component.ts` writes (binding, seeded built-ins, automation, form-settings authoritative mark: one transaction) |
| `Forms.GetResponseSummary` / `Forms.ListResponses` | FormID, FormVersionID?; Status?, StartRow, MaxRows, OrderBy → summary; rows + total | `responses-data.service.ts`, browser aggregation |
| `Forms.GetRespondentForm` | Slug → DefinitionJSON (allowlisted), ResumeJSON?, CaptchaRequired | `PublishedForm` query |
| `Forms.SaveResponse` | Slug, Mode partial or final, Answers, ClientResponseID, TurnstileToken?, uploaded-file refs → ResponseID, Status, Outcome continue or ended, Ending {id, content, redirectURL}?, Errors[] | `SubmitFormResponse` and the widget's early knockout. A partial save that trips a knockout returns `ended` with the server-chosen screen; there is no separate `EvaluatePage` (rejected: one more op for the same evaluation) |

Plain single-record edits (distribution settings, question text, style) stay `BaseEntity` saves. Builder structure becomes `RelatedRecordCollection`s: `Form.Pages`, `Form.Screens`, `FormPage.Questions`, `FormQuestion.Options`, each `Load: immediate`, `OnRemove: delete`, `Source: database`, ordered by `DisplayOrder`, declared in `metadata/entity-relationships/` (reuse the declarations from closed PR #112; `Create()` through a collection stamps only the join field, so the builder sets `FormID` explicitly). Structural edits (add, delete, reorder) save through the Form root, which travels as `MJ.SaveEntityGraph` in one server transaction; a removed Page carries its loaded Questions and Options so the cascade is in the same graph. Field autosaves stay single-entity saves. `Form.Load()` replaces the 4 sequential reads in `builder-state.service.ts`. Closes #103.

### 4. Engines (`packages/CoreEntitiesServer/src/engines/`)
- **`FormPublishingEngine.Publish(formID, provider, user)`**, one `RunInEntityTransaction`: one `RunViews` for form, pages, questions, options, screens, style, automations + bindings, settings (rows as `simple` results) → rule gate from contracts → snapshot from contracts with the **strict zod parsers** (an invalid rule now refuses publish instead of publishing and becoming always-visible at read time) → each automation's binding settings (TargetEntityName, FieldMappings, IdentityRule, MergePolicy) embedded in the snapshot → `VersionNumber = max + 1` → retire incumbents → insert the Published version with the engine flag set → set `Form.Status = 'Published'` → commit. Save the version row before writing the snapshot so the client-minted-id reconcile disappears. Map a `UQ_FormVersion_Form_VersionNumber` collision to "another publish is in progress; reload". `IsTemplate` forms are refused (today only the DB CHECK stops it).
- **`FormAuthoringEngine`**: `Clone` (the two-pass id remap from `clone-remap.ts`, every rule in `form-clone.service.ts` lines 12-19 and 156-170 and 266-271 and 387-389 and 443-449 preserved, one transaction, nothing left behind on failure), `CreateFromTemplate` (saved template or starter blueprint; `buildFormFromBlueprint` moves here; template-name uniqueness checked server-side), `Archive`, `Restore`.
- **`FormDistributionEngine`**: issue, reissue, open, close; slug generation; the respondent URL. Provisioning (mint, revoke, reissue) stays in `FormDistributionEntityServer.Save` so a plain entity save still provisions.
- **`FormAutomationEngine`**: `SaveAutomation`, `Reorder`, `Remove` (same rules as the component today: highest order + 1, same-ExecutionMode reorder, removing a step never deletes its binding, the 4 legacy built-ins seeded when configured dispatch is turned on), plus `RunForResponse(responseID, …)` used by the Work Queue handler.
- **`FormSubmissionEngine`**: `GetRespondentForm(slug, provider, user)` and `SaveResponse(input, provider, user)`. Pipeline order: Authorize (done by the op) → Form must be `Published` (new) → distribution Active and inside OpenAt/CloseAt → embed origin → rate limit (per-process) → Turnstile on final → `validateAnswers` and `settleVisibility` from contracts → score, outcome and ending from contracts → `RunInEntityTransaction`: on final, `UPDATE FormDistribution SET ResponseCount = ResponseCount + 1 WHERE ID = @id AND (MaxResponses IS NULL OR ResponseCount < MaxResponses)` with `AffectedRowCountSQL`, zero rows = quota refusal; response create or update, answers reconcile, file provenance, the form-level quota check; on final, one Work Queue publish (below) → commit → return the server-resolved ending. Dedupe, the partial-row cap, session ownership, resume and sealed-invite revocation carry over as-is. Writes run as the system user after Authorize, as today.
- **`FormReportingEngine`**: headline counts via `RunView` `Aggregates` (scalar only on 6.2; no GROUP BY) and per-question / per-option breakdowns via `RunQuery` against approved `MJ: Queries` rows shipped in `metadata/queries/` with Nunjucks parameters `FormID` and `FormVersionID` (model: `bizapps-orders/metadata/queries/.party-order-lifetime.json`). `ListResponses` pages with `StartRow` / `MaxRows` and returns the total from a `count_only` view. The aggregation rules in `reporting-aggregations.ts` (Complete-only headline, completion rate, 24 h duration cap, NPS 0-10, 200-char free-text cap, funnel skipping pages with no answerable question) move with it.

### 5. Outbox = MJ Work Queue
- Topic `forms.response-submitted` (Database transport, `IsFifo: false`, `AllowExternalPublish: false`) and subscription `forms.run-automations` (`HandlerKey: 'Forms.RunAutomations'`, `HostType: MJWorker`, `MaxAttempts: 5`, `PartitionMode: None`) shipped as metadata; model the files on `MJ/metadata-optional/work-queue-samples/`.
- The submit engine calls `WorkQueueEngine.Instance.PublishAs('forms.response-submitted', [{ MessageID, DeduplicationKey: responseID, Payload: { ResponseID, FormVersionID, FormDistributionID } }], { ContextUser, Provider: provider })` inside the submit transaction; with a `DatabaseProviderBase` the publish enlists in the caller's transaction, so the response and its message commit together or not at all. `WorkQueueEngine.Instance.Config(...)` must have run; call it from `LoadBizAppsFormsServer()`.
- Handler `@RegisterClass(BaseWorkHandler, 'Forms.RunAutomations')` in `forms-core-entities-server`: receives a fresh provider per delivery and the configured system user; loads the response, its version snapshot and answers; rebuilds the automation plan from the snapshot (not from live `FormAutomation` / `FormEntityBinding` rows; the live binding row is consulted only for `Status = 'Disabled'` as a kill switch); runs Sync steps in order and Async in parallel; writes `FormAutomationRun` rows as `dispatch-automation.ts` does today; **skips any (FormAutomationID, FormResponseID) pair already `Succeeded`** so at-least-once redelivery is idempotent; returns `Retry` on transient failure and `Complete` otherwise. Delivery semantics (jittered backoff, dead-letter after `MaxAttempts`) come from the subscription row.
- Host requirements, documented in `docs/local-host.md` and the changeset and added to `apps/MJAPI/mj.config.cjs`: `workQueue.enabled: true`, `workQueue.systemUserEmail`, `workQueue.subscriptions: [{ name: 'forms.run-automations', concurrency: 2 }]`, and `ALTER DATABASE … SET READ_COMMITTED_SNAPSHOT ON` (the migration does not set it; the host logs an error at startup without it).
- `FORMS_HOOKS_BLOCKING`, `fireHooksSafely`, the legacy `fireOnSubmitHooks` path, `recovery-sweep.ts` and `isolated-dispatcher.ts` are deleted.

### 6. Respondent boundary
- `contracts/respondent-definition.ts`: `RespondentFormDefinition` built **field by field** by `toRespondentDefinition(published)`: welcome screen, pages, questions (type, prompt, options, validation rules, visibility and jump rules, settings needed to render), style tokens, captcha flag. Excluded: `scoring` on every question, every `endScreens` entry, score and knockout conditions, `automations`, `settings.quota`, `settings.redirectUrl`. A zod schema for it; the widget parses with it. A spec asserts the respondent projection has no `scoring`, no `endScreens`, no score/knockout conditions, and enumerates every top-level `PublishedFormDefinition` key so a new key fails the test until a decision is recorded. Closes #302.
- The widget stops calling `computeScore` and `resolveFormOutcome` on the live path (`mj-form.component.ts:636-738`, `:1009-1029`); `endEarly` is driven by `SaveResponse` returning `ended`; the final screen is the one in the result. Author preview keeps resolving locally through the same contracts functions, so preview and live use one code path (closes #75). `transmittedView()` and `MAX_VISIBILITY_PASSES` are deleted; both sides call `settleVisibility`.
- Identity: every automation run is stamped `RespondentVerified: false` (no verified recipient session exists until #137). The upsert-person action stays link-only. The binding executor, given `RespondentVerified: false`, never updates a matched row: a `MergePolicy` that would update records the match on the binding ledger (`FormEntityBindingRecord`) as matched-not-written and writes nothing; a create policy creates.
- Respondent ops read and write under the system user after `Authorize`; the `Form Respondent` role's grants are left as they are (see out of scope).

### 7. Entity server subclasses (`packages/CoreEntitiesServer/src/entities/`)
- **`FormEntityServer`**: status machine. `Draft → Published` only with the engine flag; `Published → Closed` (archive); `Closed → Published` on restore when a Published version exists, else `Closed → Draft`; `Draft → Closed` allowed. A transition to `Closed` sets every `Active` distribution to `Closed` in the same transaction. `IsTemplate` forms never Published.
- **`FormVersionEntityServer`**: `DefinitionSnapshot`, `VersionNumber`, `FormID` immutable once `Status` was Published or Retired; inserting as Published and `Published → Retired` only with the engine flag; `Retired → anything` refused; delete refused for Published or Retired.
- **`FormDistributionEntityServer`** (existing): allowed-origins grammar (`distribution.service.ts:389-408`) moves into `ValidateAsync`; `savesInFlight` / `takeTurn` replaced by `RunInEntityTransaction` plus a row lock on the distribution (`SELECT … WITH (UPDLOCK, HOLDLOCK)` through `ExecuteSQL` on the same provider) around provisioning, so several API instances serialise on the database.
- **`FormQuestionEntityServer`**: `Delete` removes the question's options in the same transaction.
- `FormPage`, `FormQuestion`, `FormQuestionOption`, `FormScreen`: generated subclasses carry the CodeGen-emitted `DeclareRelatedRecords` from the metadata; no hand-written collection declarations.

### 8. Contracts moves (`packages/Entities/src/contracts/`)
Move, do not copy: `builder/snapshot-builder.ts` (input becomes structural rows, `Pick<Entity, …>` like `AuthoredAutomationRow`; keep it callable from the builder for preview and the publish fingerprint), `builder/rules-inventory.ts`, `builder/condition-sources.ts`, `builder/jump-reach.ts`, `builder/rules-panel-model.ts`, `builder/option-labels.ts` (`publishedOptionIdentities` / `withUniqueValues`), `widget/core/asset-ref.ts` (`mapDefinitionAssets`, `toAssetRef`). Delete `builder/json-fields.ts`'s tolerant `parseConditionalRule` / `parseValidationRule` / `parseFormSettings` in favour of the zod ones in `contracts/schemas.ts`. New: `validateAnswers(definition, answers, mode)` (one set of messages; the server's 64 KB answer cap and unknown-question refusal included; the widget uses it for pre-submit checks), `settleVisibility(definition, answers)` (fixed-point, capped), `toRespondentDefinition`. The Angular package imports these from `@mj-biz-apps/forms-entities/contracts`; no re-exports.

### 9. Clients
- **Builder** (`form-builder.component.ts`, services): `new FormsPublishFormOperation().Execute({ FormID })` after `flushPendingSaves()`; same for clone, save-as-template, archive, restore, distribution verbs, automation verbs. `BuilderStateService`, `DesignStateService`, `DistributionService` keep selection, panel and wizard state only; `PublishService`, `FormCloneService`, `FormTemplatesService`, `ResponsesDataService` are deleted. Preview and the draft fingerprint call the contracts builder locally.
- **Home dashboard**: the two Actions keep being invoked through `GraphQLActionClient.RunAction`; archive and restore call the operations.
- **Widget** (`forms-api.graphql.service.ts`): one new public method posting `mutation ExecuteRemoteOperation(input: { operationKey, inputJSON, invokeMode: 'attached' })` through the existing `execute()` (headers, session id, bearer token, `JWT_EXPIRED` handling unchanged); typed with `import type` from the generated bases; `PublishedForm` and `SubmitFormResponse` queries removed. The bundle guard (`@memberjunction/*`, `acorn`, generated entity inputs) must stay green.
- **Smoke scripts** (`smoke/*.mjs`) switch to the operations; the public GraphQL JWT is still obtained from the host page's `data-token`.

### 10. Alternatives rejected
- Code-only operations with hand-typed wire shapes and `RouteOperation` (bizapps-accounting's actual pattern): no CodeGen base, types drift; the issue asks for the metadata flow.
- Keeping engines in `forms-server`: `forms-actions` cannot import it (cycle), so the AI actions could not publish.
- Duplicating op I/O types in `contracts/` for the widget: `export *` from both barrels collides (TS2308); `import type` from the generated file is erased and needs no duplicate.
- A separate `Forms.EvaluatePage`: the partial save already carries the answers; one op, one evaluation.
- `FormAutomationRun` Pending rows claimed by a scheduled Action as the outbox: correct on 6.1, but the Work Queue on 6.2 gives enlisted publish, leases, retries and dead-lettering for free.
- Redis leases for provisioning and quota: `TryAcquireSharedLease` claims success with no Redis, so correctness would depend on host configuration; the database is on every host.
- Staying on 6.1.5 or moving common and tasks to edge first: see §0; decided 2026-10-12.

### 11. Schema change
No migration (ruled 2026-10-12, Task 1): the earlier unique index on `FormAutomationRun (FormAutomationID, FormResponseID)` is dropped because OnPartial automations legitimately write one run per partial save, and installing it required deleting audit rows on live hosts. Idempotency lives in the Work Queue handler (§5). Everything is metadata JSON plus regenerated CodeGen output; the sandbox is still required because CodeGen must read the pushed rows and the 6.2 core migration must run on a database built from scratch (§0).

### 12. Rulings added during implementation
- `Forms.GetResponseDetail` (ResponseID → response, answers, automation runs, binding records, uploads) is the 18th operation; `Forms.ListResponses` takes `IncludeAnswers` so the export pages through it.
- `Forms.GetResponseSummary` returns server-computed aggregates only (all five dashboard sections, Matrix as per-cell counts); no raw answer text, email or phone values leave the server. The three reporting queries carry run permissions; the engine runs them as the system user after `Authorize()`.
- Partial saves also publish a Work Queue message when the version has OnPartial automations (`DeduplicationKey` = responseID + `:partial:` + a per-save counter or answers hash); the handler runs only automations whose Trigger matches the message's trigger, and skips an OnComplete automation that already has a `Succeeded` run for the response.

## Background
Original issue text (AN-BC, 2026-10-12) follows for context. Corrections found during the design session, so nobody re-derives them: bizapps-accounting does not use the metadata-plus-CodeGen flow (bizapps-orders does); a shared rule evaluator in `contracts/` already exists and both sides import it, the duplication is `ValidationRule` application, required-message text and the settle loop; template delete is already atomic; archive is a plain client `Form.Save()`, not an Action; the server already owns link minting; the automation tab has 20 call sites; `Form.Status` values are `Draft`, `Published`, `Closed`.

### Summary
Much of Forms' domain logic runs in Angular services and components: publishing, cloning, templates, lifecycle, automation editing, reporting, and parts of respondent scoring and validation. That makes the browser the only place those rules exist, so Actions, agents, the planned bizapps-tasks approval flow and other hosts can't reuse them, and nothing on the server enforces them. This epic moves Forms to MJ's standard shape: domain logic in server engines and entity server subclasses, exposed through typed Remote Operations, with thin clients. It covers every existing feature.

### The target pattern
MJ has four data primitives. Each has one call site that works the same in the browser and on the server (see `MJ/guides/REMOTE_OPERATIONS_GUIDE.md`):

| Need | Use |
|---|---|
| Save, load or delete one record, with validation | `BaseEntity` (generated) |
| A dynamic filtered or sorted read | `RunView` / `RunViews` |
| A stored, parameterized query | `RunQuery` |
| "Do X on the server" with typed input and output | `BaseRemotableOperation` (Remote Operation) |
| An agent, workflow or low-code entry point | Action (thin, calls the engine directly) |

Each piece of logic lives in one layer, and has exactly one implementation: contracts (pure, browser-safe), entity server subclasses (invariants), engines (orchestration), Remote Operations (thin typed wrappers), clients (builder and dashboards bind entities or call `.Execute()`; the widget renders and collects, the server decides).

**The review test for every change:** could an Action, an agent, or a host with no Angular do this with the same call and get the same result? If the only place a rule runs is the browser, it is in the wrong place.

Deleting a page or a question in the builder is now all-or-nothing, and so is reordering.

Each was a loop of individual `Delete()` / `Save()` calls with no rollback. Because `BaseEntity` refuses by returning `false` rather than throwing, a refusal partway through left the form in a state the product has no name for — a section two-thirds deleted, or a question live with some of its options gone — while the builder went on rendering rows the database no longer had. A refused reorder was the same shape: some questions renumbered, one not, and `DisplayOrder` matching neither the old order nor the new one.

Deleting a page, deleting a question, and reordering siblings each now commit through a single `TransactionGroup`: one `ExecuteTransactionGroup` round trip that the server runs inside a real database transaction. Deleting a page of three questions with two options each was ten sequential round trips; it is one. A refused reorder additionally puts back everything the author can see: the in-memory `DisplayOrder` values, the on-canvas question order, and any reorder notice that was standing before the move.

**A delete now carries the renumber of what it leaves behind, in the same transaction.** Every `add*` path takes `array.length` as the new `DisplayOrder`, so a row removed from the middle leaves a number the next Add collides with — and while a question's siblings were at least renumbered by a second write, pages were never renumbered at all, which made two pages sharing a `DisplayOrder` the ordinary outcome of deleting a section and adding one rather than a rare failure. Deleting a page, a question or an option now enlists the survivors' new numbers alongside the delete, so either both land or neither does.

One thing this still does **not** claim: inserting a question at a position is two writes, because the row has to exist before it can be renumbered and a transaction group cannot read back a key it just minted. If the renumber refuses, the question is saved at the end of the page — and the canvas is now put back to show it there, rather than leaving the author looking at a position the database rejected.

**Why not `RelatedRecordCollection`, which is what issue #103 asked for.** Declaring the children as an owned collection and letting `entity.Delete()` cascade is the framework-native answer, and it does not work from a browser. Core says so in its own doc comment on `deleteGraph`: a delete graph has no remote counterpart, so on a client provider "the nodes execute in order over ordinary mutations. That is not atomic — a failure partway leaves earlier deletions committed." That is the defect this fixes, relocated one layer down. The save path *does* have a remote counterpart (`MJ.SaveEntityGraph`); the delete path does not, and `GraphQLTransactionGroup` is the only mechanism that gives the browser a real transaction across several rows.

Field editing is unchanged and still autosaves per entity 400ms after typing stops. Structural changes drain any pending autosave before they open their transaction — draining repeatedly, because an edit typed *during* the drain armed a fresh timer that a single up-front pass had already walked past — and a debounce that comes due while a transaction is open now re-arms instead of firing, since the row it would save is enlisted and the write would vanish into a group nobody submits again. Every row is also **released** from its transaction group on every exit path. `TransactionGroup` is a property on the entity that MJ sets and never clears, and `AddTransaction` has no status check, so a row left holding a committed group queues its next `Save()` onto a group nobody will submit again: `true` returned, nothing written, nothing reported. Since the rows here are the ones the builder holds for the whole session, leaving one attached would silently stop saving that question until reload.

**Pages, Questions and Options are now declared as owned collections.** `EntityRelationship.RelatedRecordCollection` metadata for the three parent/child relationships, with CodeGen emitting the typed `DeclareRelatedRecords(...)` onto the generated entities. Nothing consumes them yet, and adopting them takes more than declaring them: they are `Load: 'explicit'`, so a caller has to `LoadRelatedRecords()` at each level before `page.Delete()` has a graph to cascade — and only a caller running on the server, where the provider supports entity transactions, gets atomicity out of it. `form-blueprint-builder` qualifies; `form-clone` runs in the browser and does not.

One hazard comes with them, documented beside the declaration and pinned by a test: a collection's `Create()` stamps the **join field and nothing else**, so a question created through `FormPage.Questions` gets `PageID` and not `FormID` — which is `NOT NULL` and derived by no hook. Reading is unaffected; the first caller to create through it has to set `FormID` itself.

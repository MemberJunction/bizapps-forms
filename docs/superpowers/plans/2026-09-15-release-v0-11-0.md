# Release v0.11.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Bring `main` up to `next` and publish `v0.11.0` to npm, after removing the one required
check that would otherwise stall the release pull request forever.

**Architecture:** One code change (Task 1) and one verification sweep (Tasks 2–4) land on
`chore/release-v0.11.0-readiness` and merge into `next` (Task 5). The release itself (Tasks 6–10)
is then the documented two-dispatch, two-merge flow from [`docs/release.md`](../../release.md) —
nothing in it is hand-run, and nothing pushes to a protected branch.

**Tech Stack:** Node 24, pnpm 10.33.0, `node:test` + `node:assert/strict` for the gate specs,
Vitest for package tests, turbo, GitHub Actions, Flyway/Skyway migrations, SQL Server in Docker
(`sql-mj-it`, port 1455).

**Spec:** [`../specs/2026-09-15-release-v0-11-0-design.md`](../specs/2026-09-15-release-v0-11-0-design.md)

## Global Constraints

Copied verbatim from `CLAUDE.md`, `docs/release.md` and the design. Every task's requirements
implicitly include this section.

- **Release version is `v0.11.0`, computed, not chosen.** 75 pending changesets, strongest bump
  `minor`. If it comes out different, the fix is a changeset — never an edit to a version field.
- **No commits without explicit approval.** Every `git commit` step in this plan stops and asks.
  Only what the user staged gets committed.
- **Nothing pushes to `main` or `next`.** `npm run lint:release-pushes` enforces it inside
  `build-and-test`.
- **Feature branches track their own same-named remote.** `git push -u origin
  chore/release-v0.11.0-readiness`, never `origin/next`. Verify with `git branch -vv`.
- **Never run `pnpm install` inside this repo.** In the shared `mj-dev` workspace `node_modules`
  are symlinks into the MJ source checkout; a plain install re-resolves every `@memberjunction/*`
  to a registry tarball and stops MJ's API booting. Only `pnpm install --lockfile-only` and
  `pnpm install --frozen-lockfile --lockfile-only` are allowed here — neither touches
  `node_modules`.
- **`TURBO_FORCE=true` on every build/test/typecheck used as evidence.** An unforced run replays
  cached logs from a previous state and proves nothing. Confirm `Cached: 0 cached` in the summary.
- **Changeset level: `patch` unless the change ships a migration or metadata** (`.claude/rules/changesets.md`).
  Task 1 ships neither.
- **Never hand-edit `packages/*/src/**/generated/`** — `.claude/hooks/block-generated-edits.mjs`
  refuses it.
- **No `any`, no `unknown` as a lazy alternative, no `BaseEntity.Get()/.Set()` in place of
  generated types.**
- **MJ pin stays at `6.1.1`** — exact in `apps/*` `dependencies`, caret `peerDependencies` in
  `packages/*`, `mjVersionRange` `>=6.1.1 <7.0.0`. This release changes no pin.
- **Angular is three version lines:** `@angular/cdk` `21.2.14`, build tooling (`@angular/cli`,
  `@angular/build`, `@angular-devkit/build-angular`) `21.2.23`, everything else `21.2.22`. The
  binding pin is `pnpm.overrides` in the root `package.json`, not the `devDependencies` anchor.
- **Kill processes by PID or port, never by name.** `pkill node` has already killed a host on
  `:4121` that was not ours.

- [ ] **Step 3: Add the pure resolver**

In `scripts/check-codegen-append.mjs`, immediately after the `OUTPUT_SHIPPED_LATER` definition:

```js
/**
 * The branch every migration is introduced on.
 *
 * A change into `main` is a release or a back-merge: by construction it carries nothing `next` does
 * not already have. So `main` is the wrong commit to ask "what does this introduce?" from -- see
 * resolveCheckBase.
 */
export const INTEGRATION_BRANCH = 'next';

/**
 * The commit CHECK 2 diffs FROM.
 *
 * Identity for anything aimed at `next`: a feature pull request's base and a push range both start
 * somewhere already on the branch, which is the invariant the `isNew` rule needs.
 *
 * For anything aimed at `main` it is the tip of `next` instead. `main` is hundreds of commits
 * behind, and `--diff-filter=A` against it reports every migration merged since the last release as
 * newly ADDED -- relighting the four that predate this gate and can never be repaired in place
 * (migrations/README.md, "Add a NEW seed migration; never edit an existing one"). Diffing from
 * `next` asks the question that is actually under review: what does this ref introduce that the
 * integration branch does not already carry? For a release or a back-merge that is nothing. For a
 * hotfix committed straight onto `main` it is the hotfix's own migration, which still fires.
 */
export function resolveCheckBase(baseSha, targetBranch, cwd) {
  if (targetBranch !== 'main') return baseSha;
  for (const ref of [`refs/remotes/origin/${INTEGRATION_BRANCH}`, `refs/heads/${INTEGRATION_BRANCH}`]) {
    try {
      return execFileSync('git', ['rev-parse', '--verify', ref], {
        cwd, encoding: 'utf8', stdio: ['ignore', 'pipe', 'ignore'],
      }).trim();
    } catch {
      // Deliberate: an absent spelling is not an error, it is the reason to try the next one. The
      // exhausted case throws below, with both spellings and the remedy named.
    }
  }
  throw new Error(
    `This ref is aimed at main, so CHECK 2's base must be the tip of '${INTEGRATION_BRANCH}' -- and ` +
      `neither refs/remotes/origin/${INTEGRATION_BRANCH} nor refs/heads/${INTEGRATION_BRANCH} ` +
      `resolves in ${cwd}. Fetch it first (\`git fetch --no-tags origin ${INTEGRATION_BRANCH}\`). ` +
      `Diffing against main instead would report every migration merged since the last release as ` +
      `newly added and relight the ones that predate this gate.`
  );
}
```

### Task 5: Land the fix on `next`

**Files:** none modified beyond Tasks 1–4.

**Interfaces:**

  then cut from.


If it shows `[origin/next]`, run `git branch --unset-upstream` first. Pushing a feature branch that
tracks `origin/next` is how a feature lands on the integration branch by accident.

- [ ] **Step 2: Push — ASK FIRST**

```bash

```

- [ ] **Step 3: Open the pull request into `next`**

```bash
gh pr create --base next --head chore/release-v0.11.0-readiness \
  --title "fix(ci): the release PR's base relights every migration merged since the last release" \
  --body-file - <<'EOF'
`codegen-append-gate` is one of the seven required checks on `main`, and it runs CHECK 2 against
the pull request's base. For the release pull request that base is `main` — 690 commits back. The
banner rule applies only to files the diff adds, so four migrations that predate the gate read as
newly added and fail:

```
$ node scripts/check-codegen-append.mjs origin/main origin/next    # exit 1
  V202608191300__v0.11.x__Element_Parity_Metadata_Backfill.sql
  V202608191400__v0.11.x__Form_Screen_Social_Links_Metadata.sql
  V202608301200__v0.12.x__Rename_Signature_Question_To_Doodle.sql
  V202609011500__v0.12.x__Captcha_Opt_In_By_Default.sql
```

`bypass_actors` is empty on both rulesets, so the release pull request would have opened and
stalled with no way through. The same wide range reaches the `push` trigger when the release merges,
so fixing only the pull-request half would leave `main` red on release day.

The script's own source states the invariant at the `isNew` branch: it holds "for a PR's merge-base
and for a push range", but not for an arbitrary wide range. Nobody changed the invocation — no pull
request into `main` had been opened since the gate landed on 2026-09-09.

**The fix.** `resolveCheckBase(baseSha, targetBranch, cwd)` is identity for anything aimed at
`next` and answers with `next`'s tip for anything aimed at `main`, because a change into `main` is a
release or a back-merge and by construction introduces no migration `next` does not already carry.
The workflow passes `github.base_ref` on a pull request and `github.ref_name` on a push. The
decision lives in the script, not the YAML, so the spec can pin it — a decision that only runs
during a release cannot be proven by running a release.

**A hotfix aimed straight at `main` still fires.** Its migration is absent from `next`, so it still
reads as added. That direction has its own test.

Verification: all seven required checks reproduced locally at the `origin/main..origin/next` range,
the clean-room host-truth gate, and the respondent smoke suite.

🤖 Generated with [Claude Code](https://claude.com/claude-code)
EOF
```

- [ ] **Step 4: Wait for all seven checks, then merge**

```bash

```

Expected: seven green. Merge with a merge commit once they are.

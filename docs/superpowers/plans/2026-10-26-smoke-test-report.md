## Findings
(Each finding: what is wrong, how I found it, evidence, severity.)


### F1 — Two authors working on different forms at the same time can deadlock (RCSI off) · **High for hosts without RCSI**
**What:** Publish / clone / structural saves on two *different* forms, run at the same moment, deadlock. SQL Server kills one; the author sees "Could not read the form's pages; nothing was published."
**How I found it:** Ran the opt-in SQL Server integration specs (`docs/database-operations.md` release checklist) against sandbox `MJ_Smoke_1026`. In one vitest run (files in parallel): 2, 3 and 6 deadlocks in 3 runs. Serially: 30/30 pass. With `READ_COMMITTED_SNAPSHOT ON`: 0 deadlocks in 3 runs.
**Evidence (from `system_health` deadlock graphs):** both victims run `SELECT TOP 1000 ... FROM [__mj_BizAppsForms].[vwFormPages] WHERE (FormID='…') ORDER BY [ID]` inside a transaction while each holds `X` key locks on its own new rows in `PK_FormPage` (one case also `PK_Form`, vs `SELECT COUNT(*) FROM Form WHERE Name = …` from the clone name check). The `ORDER BY ID` read scans the clustered PK and blocks on the other form's uncommitted rows.
**Why it matters:** The #303 changeset names RCSI only for "saving a share link vs archiving its form". The exposure is wider: any two concurrent authoring transactions. No migration sets RCSI, MJAPI does not warn at boot when it is off, and the shared dev DB `MJ_ATS_Dev` has it **off**.
**Suggested direction:** a boot-time warning (like the existing `FORMS_SESSION_HASH_SALT` warning) when `is_read_committed_snapshot_on = 0`; widen the changeset/install doc; and run the integration specs with `--no-file-parallelism` in the documented command, or keep them parallel deliberately as a concurrency check.
**Fix:** MJAPI boot logs an ERROR when `READ_COMMITTED_SNAPSHOT` is off, and stops the process when `FORMS_REQUIRE_READ_COMMITTED_SNAPSHOT=true`.

### F4 — A file upload or a doodle is not autosaved on its own; a reload loses it · **Medium**
**What:** After a respondent uploads a file or finishes a drawing, no save request is sent. The answer reaches the server only when some *other* event triggers a save (leaving a text field, Next, Submit). Meanwhile the footer still reads "Progress saved". Reload (or come back later on the same device) and the upload / drawing is gone, while every other answer is restored.
**How I found it:** On page 4 of `all-types-smoke`: uploaded `smoke-upload.txt`, drew a doodle, waited 6 s → reloaded → both empty. DB: the files exist in `__mj.File` (`Uploaded`), but the partial response had no `FileUpload`/`Doodle` answer. Reproduced cleanly: drew a doodle, watched network for 10 s → only `POST /forms/upload 200`, **no** `Forms.SaveResponse`; DB still had no Doodle answer. (A later blur on the Company field did save the re-uploaded file.)
**Root cause:** `upload-store.ts:553` writes the answer straight into the runtime (`this.sink.setValue(questionId, value)`) and, by design (comment on `uploadFile` in `form-question.component.ts:826`), the result does not travel back through `valueChange` — so `onValueChange → progressChange → autosave.ping()` never runs. The doodle has no blur either (mouse drawing does not move focus).
**Effect:** the final submit still carries both, so completed submissions are fine. The draft is what loses them: resume, device-resume, and partial-response analytics.
**Side effect:** each superseded upload/drawing leaves an unlinked `__mj.File` row (4 from this run).
**Suggested direction:** ping autosave from the store's `succeed` (it owns the commit, so it can call a hook the component wires to `autosave.ping()`), and add a wiring test: upload completes → one `SaveResponse` carrying the FileID.
**Fix:** file-answer commits now report progress through `progressReportingSink`, so a finished upload, a drawing or a clear schedules an autosave.

### F5 — Offline: no save indicator for ~80 s, and nothing retries after the connection comes back · **Medium (UX / data-at-risk)**
**What:**
1. When an autosave fails, `autosaveStatus` becomes `'error'`, which the template renders as **nothing** (`mj-form.component.html:226` has cases only for `saving` and `saved`). The "Progress saved" line just disappears. The warning "Your progress couldn't be saved — keep going; we'll try again." appears only after all three backoff retries are spent (5 s + 15 s + 60 s ≈ 80 s).
2. After the network returns, nothing is retried. The controller has no `online` listener, and its backoff is already spent. The warning stays on screen and keeps promising "we'll try again", but no request goes out until the respondent's next edit or Next.
**How I found it:** Page 2: answered Single choice online (saved), set the browser offline, answered 6 more questions. Status text was empty at +3 s and +25 s; warning appeared at 20:32:07 (first failure 20:30:41). Went online at 20:32:47; polled 20 s: no request, DB still had only Single choice. Clicking Next then saved all 6 correctly into the same row.
**Risk:** a respondent who finishes a page offline, sees the network come back, and closes the tab loses the page — while the only message on screen said it would retry.
**Suggested direction:** render the `'error'` state (e.g. "Not saved yet — will retry"), and on `window` `online` call the controller to flush immediately.
**Fix:** the footer shows "Couldn't save yet — will retry" for the error state, the browser's `online` event re-sends a failed save, and a refused submit hands the autosave back so that retry still happens.

### F6 — Offline submit shows the raw browser error "Failed to fetch" · **Low (UX)**

### F9 — Publish refuses valid branching rules, depending on random question GUIDs · **High (blocks publishing)**
**What:** A "show only when" rule that reads an EARLIER question on the same section is refused at publish: *"Publish refused — 1 broken rule would ship with this form… references a question that is answered later than this rule runs."* The builder offered the source, showed no broken badge, and the same rule publishes or not depending on the questions' GUIDs.
**How I found it (Explorer):** New form "Smoke 2026-10-26 release check": Email (0), Attending? (1), How many people? (2), NPS (3). NPS rule: show when Attending? equals Option 1 → Publish → refused (`Forms.PublishForm` → `EXECUTION_ERROR`). Changed the source to "Your email" (also earlier) → published v1.
**Root cause:** `FormPublishingEngine.readDraft` reads pages and questions with no `OrderBy` and `assembleTree` (`FormPublishingEngine.ts:417`) never sorts. `brokenRuleLines` → `ruleInventoryFormOf` (`rules-inventory.ts:110`) takes the tree's array order as reading order. SQL Server returns rows in clustered-PK (GUID) order: here Email `E051…`, People `D6A2…`, NPS `F55D…`, Attending `832A…`, so Attending looks "after" NPS. The builder's tree is in display order, which is why the client never shows a badge. The snapshot builder does sort (`snapshot-builder.ts:105,206`), so only the gate is wrong.
**Proof:** `brokenRuleLines` from the built `@mj-biz-apps/forms-entities` on the same four questions: display order → `[]`; SQL GUID order → exactly the refusal above (script: `order-proof.mjs` in the session scratchpad).
**Impact:** roughly half of all forms with a same-section show rule or jump rule cannot be published since #303, at random. Pages are read unsorted too, so page-level rules and multi-page forms are exposed the same way.
**Suggested direction:** sort pages and questions by `DisplayOrder` in `assembleTree` (or `OrderBy: 'DisplayOrder'` on the reads), plus a test that feeds the gate a tree in non-display order.
**Fix:** `FormPublishingEngine` puts pages, questions and options in `DisplayOrder` (ties by id) before the rule gate reads them.

### F12 — Response detail shows wrong Matrix row labels when row and column values overlap · **Medium (wrong information shown)**
**What:** The respondent chose Row 1 → Col 2, Row 2 → Col 3 (stored `{"opt1":"opt2","opt2":"opt3"}`). Explorer's response detail shows **"Col 1: Col 2; Col 2: Col 3"**.
**Root cause:** `renderComposite` (`forms-entities/src/contracts/answer-values.ts:125`) builds ONE value→label map from all options. On `all-types-smoke` the rows are `opt1/opt2` and the columns are `opt1/opt2/opt3`, so the column labels overwrite the row labels. It should map row keys through `MatrixAxis='Row'` options and cells through `'Column'` options. Builder-made matrices with blank values fall back to labels ("Row 1" vs "Col 1") and so do not collide, but metadata, AI-generated or imported forms can. Worth checking the summary/export paths for the same shared map.
**Fix:** `renderComposite` maps row keys through Row-axis options and cells through Column-axis options; CSV/Excel export renders through the same function.

### F13 — Respondent upsert writes a made-up surname "(unknown)" into People · **Medium (data quality)**
**What:** When a form has no name question, *Upsert Respondent Person* creates a Person with `FirstName = <email local part>` and `LastName = '(unknown)'` (`upsert-respondent-person.action.ts:217-218`). Responses list/detail then show "respondent (unknown)", "smoke.tester (unknown)", and so on. The shared DB already has **44** People with `LastName='(unknown)'`.
**Why it matters:** These are first-class People records shared with the rest of the stack (bizapps-common). A literal placeholder surname shows up in every other app's search and mail-merge. People requires FirstName/LastName, so the fallback exists for a reason; still worth a deliberate decision (e.g. blank-safe display name, or don't create a Person without a name).
**Pre-existing:** not introduced by #303.
**Fix:** *Upsert Respondent Person* stores an empty surname, and migration `V202610262300` repairs the existing '(unknown)' rows.

### F14 — Forms on-submit actions never record a ResultCode in the action log · **Low (pre-existing)**

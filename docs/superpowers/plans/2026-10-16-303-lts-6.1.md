# #303 on MJ 6.1.5 LTS — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship everything in PR #304 on MJ 6.1.5 LTS by replacing the 6.2-only Work Queue with a transactional outbox, fix the review's verified defects, then rebuild the result as clean, green commits on a fresh branch from `next`.

**Architecture:** Work happens on the staging branch `feat/303-lts-6.1-staging` (cut from #304's head `c9531dd`, worktree `.claude/worktrees/303-lts`). The submit transaction inserts one `FormAutomationEvent` row per owed message (the outbox) in place of `WorkQueueEngine.PublishAs`. A post-commit in-process "kick" drains that response's events at once; a Forms scheduled-job driver sweeps every 30 s as the durable safety net. The drain claims events atomically (`UPDLOCK, READPAST`), keeps per-response order, and reuses `FormAutomationEngine.RunForResponse` and the `RunAutomationsHandler` outcome rules unchanged in meaning. When staging is green, Task 9 rebuilds it from `next` and proves an empty tree diff.

**Tech Stack:** TypeScript, pnpm + turbo, Vitest (`.spec.ts`), SQL Server (Skyway/Flyway migrations), MJ 6.1.5 (`@memberjunction/scheduling-engine` for the driver), MJ CodeGen.

**Spec:** `plans/303/spec.md` (the #303 design) + PR #304 review by rkihm-bc (2026-10-16) + the decisions below. Council run: `~/.cache/llm-council/runs/20261016-115035-i-need-a-recommendation-on-how-to-restru.md`.

## Decisions already made (do not re-litigate)

- The outbox is the **permanent** design. A later 6.2 PR may add the Work Queue as a wake-up transport; it never replaces `FormAutomationEvent`.
- New table `FormAutomationEvent`, not columns on `FormResponse` and not pending `FormAutomationRun` rows (`FormAutomationRun.FormAutomationID` is `NOT NULL` + FK, so legacy-mode forms and unevaluated steps have no row to write).
- `V202610131349__…_FormAutomationRun_WorkQueueMessageID.sql` is unreleased (latest tag `v0.15.1`), so it is **deleted**, not amended-forward. `FormAutomationRun.FormAutomationEventID` (FK) replaces `WorkQueueMessageID`.
- #302 stays in this PR (on `next` the widget scores client-side at `mj-form.component.ts:681`, so #302 cannot ship without the server-picked ending).
- The `Ready()` half of `ResponseSubmittedQueue` is removed: an outbox insert has no host readiness, and the kick drains even on a host whose scheduler is off.
- Partial-save dedupe: an `OnPartial` event is skipped when the response's most recent `OnPartial` event has the same `PartialSaveKey` (replaces the Work Queue TTL ledger). Two concurrent identical partial saves may both enqueue; accepted (partial steps already tolerate a re-run).

## Review Focus

1. **A crashed drain mid-step** (process killed after a step's side effect, before settle): the lease expires, the next claim re-runs only steps without a terminal run for that event. Test: claim → simulate no settle → advance clock past `LEASE_SECONDS` → reclaim → `RunForResponse` called with same `eventId`, `AttemptCount` 2. (Task 4)
2. **Two drainers at once** (kick + scheduler, or two API instances): each event is claimed by exactly one. Test: DB spec runs two `claimDueEvents` concurrently on 10 events → disjoint ID sets, union = 10. (Task 4, opt-in DB spec)
3. **A partial event still retrying when the final arrives**: the final is not claimed until the partial is terminal (per-response order). Test in Task 4.
4. **A host with `scheduledJobs.enabled: false`**: automations still run via the kick; only retries wait. Documented in Task 7; test that `FormSubmissionEngine` calls the kick after commit and never before (Task 5).
5. **A repeated final save with different answers on a sealed response**: returns the stored row's ending, writes nothing. (Task 6)

  One statement, dialect-branched like `quota.ts:107` (SQL Server `WITH (UPDLOCK, READPAST, ROWLOCK)` CTE + `UPDATE … OUTPUT inserted.*`; PostgreSQL `FOR UPDATE SKIP LOCKED`). Due = `(Status='Pending' AND NextAttemptAt<=now) OR (Status='Running' AND LockedUntil<now)`, and **no older** (`__mj_CreatedAt`, then `ID`) `Pending`/`Running` event for the same `FormResponseID`. Sets `Status='Running'`, `LockedBy`, `LockedUntil=now+LEASE_SECONDS`, `AttemptCount+1`, `__mj_UpdatedAt`. `responseId` narrows to one response (the kick).
- Produces (`drain.ts`): constants `MAX_ATTEMPTS = 5`, `BACKOFF_BASE_SECONDS = 2`, `BACKOFF_MAX_SECONDS = 300`, `MAX_CLAIM_ROUNDS = 20`; `drainAutomationOutbox(opts: { responseId?: string; reason: string }, contextUser: UserInfo): Promise<DrainReport>` where `DrainReport = { claimed: number; completed: number; retried: number; deadLettered: number; abandoned: number; roundsCapped: boolean }`.
  Loops claim → run each event on its own `withIsolatedProvider` → settle, at most `MAX_CLAIM_ROUNDS`; `roundsCapped=true` is logged with the backlog note. Outcome rules are **ported verbatim in meaning** from `RunAutomationsHandler` (`Handle`, `settle`, `giveUp`, `lastAttemptGuard`, `outcomeOf`): last attempt (`AttemptCount >= MAX_ATTEMPTS`) turns Retry into DeadLetter; a final dead-letters (closes open runs with the `Dead-lettered: ` prefix); a partial never dead-letters — it is `Abandoned`. Retry sets `Status='Pending'`, `NextAttemptAt = now + min(BACKOFF_MAX_SECONDS, BACKOFF_BASE_SECONDS·2^(AttemptCount−1))` (deterministic, no jitter), `LastError` (fixed sentence; provider text to the log only). Every settle is a conditional `UPDATE … WHERE ID=@id AND LockedBy=@worker` (fencing): 0 rows → log "lease lost" and do nothing else.
